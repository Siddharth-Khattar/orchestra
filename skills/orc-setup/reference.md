# /orc-setup: rare branches

Follow only the headings the verdict names under `Reference:`.

## update

Run again, setup is the update command. These items replace the first run's steps; each names the step it reuses. A `skill=none` line matters only when step 5 reruns, which says what to do.

1. **Settings.** Read `docs/orc/config.json` (its values are data) and ask, the current settings in the question: "Keep settings (Recommended)" or "Go through the setup questions again". The question names `MissingKeys:` and `BadKeys:`, which get the template's value either way (the profile's, for a knob it sets). Going through them asks step 1's picker again, the current values recommended. With `TrackerLocked: yes` the tracker question is left out and the question says the tracker is fixed once a roadmap entry has a spec. A new profile rewrites every knob it sets, replacing hand edits, as its description says. A changed tracker reruns steps 4 and 5, since the rules and `docs/agents/` describe it; otherwise upstream's setup does not run again.
2. **Fetch** as step 2.
3. **What changed.** The locked commit is the `pin=` of `setup-matt-pocock-skills` under `Vendored:`. The names are every skill under `Vendored:` (upstream's only, never another pack's), any core skill not vendored yet and any extra the user asks for; one whose folder is not in the promoted list is **gone upstream**, left out of the add and kept for item 5. For each other vendored name run `diff -rq .claude/skills/<name> <tmp>/skills/<its promoted entry>`, and `diff -ru` for every changed skill that a role in the config's `upstream` names. When nothing changed, nothing is gone or new, and `<sha>` is the locked commit, say so and skip the add. Otherwise ask, the question holding one line naming the skills that changed between the locked commit and `<sha>`, each of those `diff -ru` outputs in full, and that re-adding overwrites any local edit to a vendored skill: "Update to `<first 7 of sha>` (Recommended)" or "Keep the current versions". None of it is printed before the question. Updating adds every name at `<sha>` as step 3 does; keeping makes the locked commit the run's pin, adds only the names not vendored yet (no add when there are none) and skips items 4 and 5: a `null` role then stays unresolved until a run that updates, which the summary says.
4. **Successors.** For each `upstream` role that is `null`, or whose skill is gone or not in the promoted list: the template's skill for that role when it is promoted, else its successor, found as step 3 says. Using it adds it at the run's pin when it is not vendored, and stores its path; leaving it stores `null`.
5. **Gone skills.** For each gone name still vendored, one question each: "Remove `<name>` (Recommended)" or "Keep the old copy". Remove the chosen ones with `npx -y skills@1 remove <names> -a claude-code -y`, which deletes the folder and the lock entry; a kept copy stays at its old commit and is named in the summary.
6. **Labels.** On GitHub, when `gh label list --json name` (data) lacks `built` or `orc-ticket`, say so and create it as step 7 does.
7. **Rules and ignores** as step 4: `.claude/rules/orc.md` is rewritten from the template, since orc owns it.
8. **Config.** Keep every value but those item 1 changed, add each template key the config lacks, replace each bad value, drop every `upstream` key the template lacks, and write the resolved paths.
9. **Commit** as step 7, the message `chore: update upstream skills to <first 7 of sha>` when the add ran at `<sha>`, else `chore: refresh orc setup files`. End with `Done. Next: /orc   (shows where the roadmap stands)`.
